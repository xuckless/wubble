## `vault-unlock-worker`: Vault unlock off the store thread

Area: todo-b. Needs an engine patch: no.

Fetching the vault key from the OS keyring can block for a long time: macOS shows a Keychain prompt, and Linux's Secret Service waits for its unlock dialog. Today `VaultCommand::Unlock` runs on the store thread, which owns the database (crates/wubble-vault/src/command.rs:215, `self.unlock()`; keyring access in crates/wubble-vault/src/keyring.rs). While the prompt is open, every save, history write and query waits behind it (TODO M7 "Hardening: vault unlock off the store thread"). Chrome reads the OS key on a separate task runner.

To build: split unlock into two steps. (1) A `KeyFetch` worker thread, owned by the vault's host side (crates/wubble/src/host/pages.rs or a vault host module), calls `KeyRing::get_or_create` and sends the result back. (2) The store thread only applies the key it is given (`Vault::unlock_with(key)`: check the key against the rows, then report Ready, Unreadable, KeyLost or NewKey). Extend the vault's lifecycle (crates/wubble-vault/src/state.rs) with an explicit `Unlocking` state. Commands that need the key while Unlocking get `NotUnlocked` (the page shows "Waiting for the keyring"), and a second Unlock request while one is in flight is merged into it. Keep the rule "the vault never replaces a lost key": NewKey is created only by the worker after the store thread confirms there are no rows, as two steps with no race. Unit tests with `FakeKeyRing` for the new transitions, including a slow fetch with saves going through meanwhile. All platforms.
