## `x11-xdnd`: X11: page drags out to other apps and drops in of links, HTML and text (XDND)

Area: page-interaction. Needs an engine patch: no.

Chrome on X11 lets a link, a text selection, an image or an HTML draggable leave the window and drop into other apps (text/uri-list, _NETSCAPE_URL, text/x-moz-url, text/html, UTF8_STRING, the image as a file), and it takes drops from other apps of files, links, HTML and text. In wubble under X11, `crate::clipboard::Clipboard` is `wayland::Wayland`, whose worker never opens, so `Host::aux()` (crates/wubble/src/host/drag.rs) falls back to `crate::wl::Null`. `drags_out()` is false, so a page drag that leaves the window ends at `Over::Elsewhere`. Drops in arrive only as winit's `HoveredFile`/`DroppedFile`, which means files only: a link or text dragged from another app into a page or onto the tab list does nothing. To build: add `crates/wubble/src/wl/x11.rs`, one worker on its own x11rb connection (MIT/Apache) that implements `crate::wl::Aux`. As drag source: own XdndSelection, an XDND source loop with XdndEnter, Position and Drop, offers built from `wubble_core::dnd`'s tables (add `_NETSCAPE_URL` for X11, as Chromium's `ui/base/x/x11_drag_drop_client.cc` does), the picture through `drag_file.rs`, and the drag image in a shaped ARGB override-redirect window that follows the pointer. On drop end it delivers `AuxEvent::DragEnded`. As drop target: set XdndAware on each window in `add_window`, read the offer with `dnd::plan`, and deliver `DropEnter/DropMove/Dropped/DropLeave`. `drop_action` answers XdndStatus. Pick X11 over Wayland in `clipboard.rs` (and drop winit's file drops for windows the worker serves) when `WAYLAND_DISPLAY` is unset. Cite Chromium's x11_drag_drop_client.cc (BSD-3) and add a THIRD_PARTY_NOTICES.md entry.

## `cross-window-page-drag`: Page drags between wubble windows, and an OS drag coming back in

Area: page-interaction. Needs an engine patch: no.

In Chrome, a link, a selection or an HTML draggable dragged from a page in one window and dropped on a page or the tab strip of another window behaves exactly like a drop inside one window. The target page gets the source's full DropData, custom types included, and the operations the source allows. Today `Host::drag_target` (crates/wubble/src/host/drag.rs) only knows the source window (`drag_window`). Outside it, a drag becomes the OS's (Wayland, macOS) or ends at `Over::Elsewhere` (X11, Windows). When the Wayland OS drag re-enters any wubble window, it comes back through `AuxEvent::DropEnter` as a foreign offer. Its data has been re-read through pipes, its custom types are gone, the source's `allowed` ops are gone, and a move of editable text becomes a copy. To build: (1) On X11, Windows and macOS, resolve the pointer's screen position against every window of the process (winit outer positions in `crate::instance`/window registry), with z-order from the last focus order. Hand the drag to the other window's host as `Over::Page`/`Over::Shell`, using `DragPhase::EnterFrom(held)` from the source view's `held_drag()`. The `wubble_core::drag` and `pagedrag` machines get a `window` field on `Over`. (2) On Wayland and macOS, recognise an offer whose source is the process's own running drag (the worker keeps the `WlDataSource` and macOS the session). Treat it as the page drag (EnterFrom(held), the source's ops) instead of an external drop. Then `pagedrag::Input::OsEnded` reports the real drop operation to the source. Pure machine changes go in crates/wubble-core/src/pagedrag.rs with unit tests.

## `drag-custom-types-out`: An HTML draggable's custom dataTransfer types (and DownloadURL) reach other apps

Area: page-interaction. Needs an engine patch: no.

In Chrome, `dataTransfer.setData('application/x-trello-card', ...)` and other custom types on a draggable go out with the OS drag as Chromium's web custom data: Linux `chromium/x-web-custom-data`, macOS `org.chromium.web-custom-data`, Windows "Chromium Web Custom MIME Data Format", each a base::Pickle of string16 pairs. Another Chromium app (Chrome, Electron, VS Code) then sees the same types. On Windows, `DownloadURL` (mime:name:url) becomes a virtual file. CEF 156's CefDragData has no getter for custom data, so `DragData` (crates/wubble-engine/src/page.rs) and welding's `DragPayload` carry none. Today custom types only survive between wubble views (welding change 54 clones the held DropData). To build without an engine patch: a helper content script (crates/wubble-helper/src, alongside clipboard.js, composed in main.rs `compose` on welding's context-script channel) adds a trusted `dragstart` listener on window in the bubble phase, after page handlers. While still in dragstart, it reads `e.dataTransfer.types` and `getData` for every type other than text/plain, text/uri-list and text/html, caps the total size, and posts them on a new `FrameChannel::Drag`. The engine attaches them to the next `DragData` as `custom: Vec<(String, String)>`. `wubble_core::dnd` gains a pure `web_custom_data_pickle(&[(String,String)]) -> Vec<u8>` (Chromium `ui/base/clipboard/custom_data_helper.cc` format, BSD-3, unit-tested) and adds the platform type to `offers`/`pasteboard`. wl/wayland.rs and wl/macos.rs offer it (X11/Windows once those exist). Agent drags stay home (decisions.md).
