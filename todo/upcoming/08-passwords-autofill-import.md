## Password Checkup: weak and reused passwords, local; compromised behind an off-by-default setting (`pw-checkup`)

Key: `pw-checkup` · engine patch: no · state: not written.

Chrome's Password Checkup lists compromised, reused and weak passwords with a "Change password" link per site. wubble has nothing of it. Build: (1) a pure module `wubble_vault::check` (or wubble-core if kept free of crypto): `weak(password) -> bool` using the zxcvbn crate (MIT; Chrome uses zxcvbn, score < 2 is weak), `reused(rows) -> groups` by comparing SHA-256 of passwords in memory only, never stored; results as `CheckReport { weak: Vec<RecordId>, reused: Vec<Vec<RecordId>>, compromised: Option<Vec<RecordId>> }`, unit-tested. (2) `VaultCommand::Check` on the store thread decrypts, computes, zeroizes. (3) Compromised: Chrome asks Google; wubble instead may query the Pwned Passwords k-anonymity range API (only the first 5 hex chars of SHA-1 leave the machine, response padding on) through the existing `ureq` dependency, ONLY when a new setting `passwords.check_compromised` (crates/wubble-core/src/settings.rs, Section::Privacy, default false) is on, run on a worker thread, results cached in memory for the session. (4) UI: a "Check passwords" row on `PasswordsPage` (crates/wubble-ui/ui/components/pages.slint) opening a list section with three groups (kit ListCard/ListRow/ListNote), each row with Edit and "Change password" which opens `https://<origin>/.well-known/change-password` (Chrome's change-password URL) in a new tab; an issue count on the page header. ## OS re-authentication before revealing, copying, exporting or editing secrets (`pw-os-reauth`)

Key: `pw-os-reauth` · engine patch: no · state: not written.

Chrome on macOS and Windows asks for the device password, Touch ID or Windows Hello before showing, copying, editing or exporting a saved password (and before filling a saved card), with a grace period of about a minute; Linux Chrome has no prompt. wubble unlocks the vault through the keyring only (`VaultCommand::Unlock`, crates/wubble-vault/src/command.rs), and Reveal/Copy run without a check (crates/wubble/src/host/pages.rs `Then::Show`, `Then::Copy`). Build: a `trait Reauth { fn ask(reason: &str) -> Result<bool, String> }` in crates/wubble (one shared trait, per-platform impls): macOS `LAContext evaluatePolicy:deviceOwnerAuthentication` via objc2-local-authentication; Windows `UserConsentVerifier::RequestVerificationAsync` (windows crate), falling back to `CredUIPromptForWindowsCredentialsW`; Linux: a no-op that returns true, as Chrome does, with an optional polkit check left out. A pure gate in wubble-core, `reauth::Gate` (one enum: `Fresh{until}`/`Stale`, `fn transition`), decides whether an action needs a prompt (60 s grace, reset on lock and when the page is left). Route Reveal, Copy, Edit (when the password field changes), ExportCsv and card fill through it in crates/wubble/src/host/pages.rs, running the prompt off the UI thread. Setting `passwords.reauth` (crates/wubble-core/src/settings.rs, Section::Privacy, default true on macOS and Windows, hidden on Linux). Unit tests for the gate.

## Vault unlock off the store thread (`vault-unlock-worker`)

Key: `vault-unlock-worker` · engine patch: no · state: not written.

Fetching the vault key from the OS keyring can block for a long time: macOS shows a Keychain prompt, and Linux's Secret Service waits for its unlock dialog. Today `VaultCommand::Unlock` runs on the store thread, which owns the database (crates/wubble-vault/src/command.rs:215, `self.unlock()`; keyring access in crates/wubble-vault/src/keyring.rs). While the prompt is open, every save, history write and query waits behind it (TODO M7 "Hardening: vault unlock off the store thread"). Chrome reads the OS key on a separate task runner.

To build: split unlock into two steps. (1) A `KeyFetch` worker thread, owned by the vault's host side (crates/wubble/src/host/pages.rs or a vault host module), calls `KeyRing::get_or_create` and sends the result back. (2) The store thread only applies the key it is given (`Vault::unlock_with(key)`: check the key against the rows, then report Ready, Unreadable, KeyLost or NewKey). Extend the vault's lifecycle (crates/wubble-vault/src/state.rs) with an explicit `Unlocking` state. Commands that need the key while Unlocking get `NotUnlocked` (the page shows "Waiting for the keyring"), and a second Unlock request while one is in flight is merged into it. Keep the rule "the vault never replaces a lost key": NewKey is created only by the worker after the store thread confirms there are no rows, as two steps with no race. Unit tests with `FakeKeyRing` for the new transitions, including a slow fetch with saves going through meanwhile. All platforms.
