## Resolve __MSG_ names from extension _locales (`ext-msg-locale-names`)

Key: `ext-msg-locale-names` · engine patch: no · state: not written.

Chrome shows an extension's localised name, description and action title: `__MSG_key__` placeholders in manifest.json are resolved from `_locales/<locale>/messages.json` (default_locale, then the UI locale with region fallback, keys case-insensitive). wubble shows them raw in the install prompt, the extension list and the footer popover (crates/wubble-core/src/extensions.rs:130 "a `__MSG_name__` placeholder is shown raw for now"; research/extensions.md "Acceptance", gap 1).

To build: a pure resolver in wubble-core (crates/wubble-core/src/extensions.rs or a new `extensions/locale.rs`): `fn resolve(text, messages: &Messages) -> String`, with `Messages::parse(json)` that follows Chromium's `extension_l10n_util` rules (an idea port of extensions/common/message_bundle.cc, BSD: case-insensitive keys, `$placeholder$` substitution from each message's `placeholders`, `$$` escape, unknown keys left as written). Add locale choice `fn pick(available, ui_locale, default_locale)` with fallback from `en_US` to `en`, then to default_locale. The I/O sits in crates/wubble/src/extensions.rs, where manifests are read at install and at start: read the chosen messages.json files (size-capped) and store the resolved name, description and `action.default_title` in `Installed`. Re-resolve when the OS locale changes at the next start. Unit tests with the Bitwarden manifest shapes. All platforms.

## Extensions shell: popup auto-size, tooltip, action menu, pinning, embedded options (`ext-popup-shell`)

Key: `ext-popup-shell` · engine patch: no · state: not written.

In Chrome, an action popup auto-resizes to its content between 25x25 and 800x600 (`ExtensionPopup`, `EnableAutoResize`). The toolbar button has a tooltip with the action title, and a right-click shows the extension's menu (name, Options, Remove from Chrome, Pin/Unpin, Manage extension, Inspect popup). Actions can be pinned to the toolbar, and `options_ui {open_in_tab: false}` options show in an embedded dialog. The global profile's `chrome.action` popups also work. wubble polls the popup page's size with a script every 150 ms (`host/ext_ui.rs`, `SIZE_SCRIPT`, `SIZE_POLL`). TODO M6 lists the rest as missing: the footer-button tooltip (needs an `Action`), the popup's own pointer origin for `<select>` lists, and global-profile popups. To build: (1) Welding change 58: `CefBrowserHost::SetAutoResizeEnabled(true, min, max)` on the popup view, with `CefDisplayHandler::OnAutoResize` pushed as a `WebEvent::AutoResized(w, h)` into `wubble-engine`. Use it when CEF delivers it for windowless browsers, else keep the script. (2) Tooltip: add an `Action::Extensions` in `action.rs` so the footer button gets the shared tooltip (`host/tooltip.rs`). Per-row tooltips show the action title from `ActionState`. (3) A right-click or long press on a popover row opens a kit menu (`wubble_core::controls::menu`) with Options, Pin to sidebar, Remove, Manage and Inspect popup. A pinned action renders as its own footer icon with its badge. Store the pins as a hidden setting. (4) `<select>` popups in the popup view take the popup pane's origin in `popups.rs`. (5) Options with `open_in_tab: false`: `Manifest` reads `options_ui.open_in_tab`, and the page opens in a kit sheet hosting a view, like the popup card at 800 max width. (6) Popups for the global profile: route its `action_click` popup URL to a view in `ContainerId::DEFAULT`.

## DevTools for extension popups, service workers and options pages (`ext-inspect-views`)

Key: `ext-inspect-views` · engine patch: no · state: not written.

In Chrome, the extension card offers "Inspect views: service worker, popup.html", and a right-click on the action offers "Inspect popup", which keeps the popup open while DevTools is attached. wubble has neither. The popup is a windowless view (`crates/wubble/src/host/ext_ui.rs::open_popup`, pane `POPUP_TAB`) that closes on an outside press, and the service worker has no view. To build: (1) In the Settings extensions list and the footer popover row, add an "Inspect" item (kit menu rows) for an extension whose `ext_api::available()` is true. (2) Popup: open CEF's detached DevTools on the popup's view (`View::open_devtools_at(None)`), or the bridge's undocked window. While DevTools is attached, the panel lifecycle (`wubble_core::extensions::shell::panel_transition`) gets a `PanelEvent::Pinned` state in which an outside press or Escape does not close the popup, as in Chrome. (3) Service worker: find its target by `Target.getTargets` (type `service_worker`, url `chrome-extension://<id>/`) over a browser-target session (`Target.attachToBrowserTarget` from any view's DevTools channel), then attach the devtools-pipe-bridge frontend with `Target.attachToTarget {flatten: true}` and route by `sessionId`. If CEF refuses the browser target to its page client, fall back to `devtools.remote_port`'s `/json/list` and say so in the row. (4) Options pages are tabs already, so F12 works there. Add pure tests for the Pinned transition in `extensions/shell.rs`.

## Chrome Web Store install and updates, behind an off-by-default setting (`ext-webstore-install`)

Key: `ext-webstore-install` · engine patch: no · state: not written.

Chrome installs from chromewebstore.google.com ("Add to Chrome" through `chrome.webstorePrivate`) and checks the update URL every few hours. wubble installs only from the user's files, with no Web Store and no updates (decisions "Extension install" and "Extension updates"; TODO M6 "install from the Web Store"). To build, all behind a new Bool setting `extensions.web_store` (default 0, `Section::Privacy`, label stating it contacts Google): (1) On chromewebstore.google.com pages, a document script (`View::set_document_scripts`) defines a `chrome.webstorePrivate` shim, ported from samuelmaddock/electron-browser-shell `electron-chrome-web-store` (MIT, with a THIRD_PARTY_NOTICES entry): `beginInstallWithManifest3`, `completeInstall`, `getExtensionStatus` and `isInIncognitoMode` answered from wubble's list. It posts to the host through a `Runtime.addBinding` binding. (2) The host downloads `https://clients2.google.com/service/update2/crx?response=redirect&prodversion=156.0.8078.96&acceptformat=crx3&x=id%3D<id>%26uc` through `crates/wubble-engine/src/fetch.rs`. Check that `host-resolver-rules` in `engine/app.rs` does not block the hosts used; `*.gvt1.com` is blocked, so either follow the redirect via an allowed mirror or add a narrow exception only while the setting is on. Then install through the existing .crx path (`engine/extensions.rs`, `parse_crx`), showing the existing install prompt. (3) Verify the CRX3 signature for store installs: RSA-SHA256 over the signed header data, with `crx_id` matching the key, ported from Chromium `components/crx_file/crx_verifier.cc` (BSD), using an MIT/Apache RSA crate. (4) Updates: a pure `extensions::update` state machine (Idle, Checking, Downloading, Ready) driving a daily omaha `update2/crx` check for store-sourced entries. A new `Source::WebStore` keeps the update URL. Tests for the shim's answers and the update machine.

## Extensions: native messaging hosts found where desktop apps install them (`ext-native-messaging`)

Key: `ext-native-messaging` · engine patch: no · state: not written.

In Chrome, `runtime.connectNative`/`sendNativeMessage` find host manifests in the user-level dirs (`~/.config/google-chrome/NativeMessagingHosts`, `~/.config/chromium/NativeMessagingHosts`, macOS `~/Library/Application Support/Google/Chrome/NativeMessagingHosts`) and the system dirs, and Windows uses the registry. Password-manager desktop apps (Bitwarden, 1Password, KeePassXC) write Chrome's and Chromium's dirs. In wubble, CEF overrides `DIR_USER_DATA`, so Chromium looks only under `<cache root>/NativeMessagingHosts` and the system Chromium paths (docs/research/extensions.md table row "nativeMessaging": "wubble's user dir needs them copied or linked (later)"). To build: (1) Core, pure: `extensions::native_hosts::plan(found: &[(source_dir, file_name, json)], installed_ids, existing_in_ours) -> Vec<HostOp>` keeps only valid manifests (`name`, `path`, `type: stdio`, and `allowed_origins` naming an installed extension id, or any `chrome-extension://` origin when the user allows it). It copies changed ones, removes ones whose source vanished and that wubble wrote (tracked by a marker field or a side list), and never overwrites a user's own file. Tests. (2) Engine: `crates/wubble-engine/src/extensions.rs` gains `sync_native_hosts(root)`, run before CEF starts next to the dictionary install, scanning the per-platform source dirs (Linux: google-chrome, chromium, BraveSoftware, microsoft-edge, vivaldi; macOS equivalents). On Windows, no copy is needed, since Chromium reads `HKCU\Software\Google\Chrome\NativeMessagingHosts` only for Chrome branding: add our own registry key mirroring entries. (3) Settings: a Bool `extensions.native_hosts_import` (default 1, local only, no network) and a list of imported hosts in the extensions section.
