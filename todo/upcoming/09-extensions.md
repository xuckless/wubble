## Resolve __MSG_ names from extension _locales (`ext-msg-locale-names`)

Key: `ext-msg-locale-names` · engine patch: no · state: not written.

Chrome shows an extension's localised name, description and action title: `__MSG_key__` placeholders in manifest.json are resolved from `_locales/<locale>/messages.json` (default_locale, then the UI locale with region fallback, keys case-insensitive). wubble shows them raw in the install prompt, the extension list and the footer popover (crates/wubble-core/src/extensions.rs:130 "a `__MSG_name__` placeholder is shown raw for now"; research/extensions.md "Acceptance", gap 1).

To build: a pure resolver in wubble-core (crates/wubble-core/src/extensions.rs or a new `extensions/locale.rs`): `fn resolve(text, messages: &Messages) -> String`, with `Messages::parse(json)` that follows Chromium's `extension_l10n_util` rules (an idea port of extensions/common/message_bundle.cc, BSD: case-insensitive keys, `$placeholder$` substitution from each message's `placeholders`, `$$` escape, unknown keys left as written). Add locale choice `fn pick(available, ui_locale, default_locale)` with fallback from `en_US` to `en`, then to default_locale. The I/O sits in crates/wubble/src/extensions.rs, where manifests are read at install and at start: read the chosen messages.json files (size-capped) and store the resolved name, description and `action.default_title` in `Installed`. Re-resolve when the OS locale changes at the next start. Unit tests with the Bitwarden manifest shapes. All platforms.

## Extensions: tabs.getCurrent and getViews for non-tab views (Bitwarden popup width) (`ext-tabs-getcurrent`)

Key: `ext-tabs-getcurrent` · engine patch: yes: waits for the one engine build · state: not written.

In Chrome, `chrome.tabs.getCurrent()` returns undefined in an action popup, and `chrome.extension.getViews({type:'tab'})` does not count the popup. In wubble, the popup and the DevTools panel are windowless views that carry a `SessionTabHelper` id. So `getCurrent` returns `{id, windowId: -1}`, and Bitwarden concludes it is in a tab and lays out 57 px wide (docs/research/extensions.md gap 2; TODO M6). Patch `53-src-non-tab-views.patch`: in `chrome/browser/extensions/api/tabs/tabs_api.cc` `TabsGetCurrentFunction::Run`, and in `extensions/browser/extension_function...`/`chrome/browser/extensions/api/runtime` `GetViews` (`ExtensionHost`/`ProcessManager` view type), consult the registry from `10-cef-tabs-windows.patch` (`cef_wubble_ext` window and tab state). A web contents whose browser id is not in the last `set_state` tab list answers `getCurrent` with no tab, and `getViews` reports `mojom::ViewType::kExtensionPopup` for views wubble marks as popups. Add a table function `mark_view(browser_id, kind)` (popup, devtools, side panel), called by wubble when it opens such a view: `host/ext_ui.rs::open_popup` and `host/devtools.rs::open_panel`. wubble side: wrap it in `crates/wubble-engine/src/ext_api.rs` (`Engine::mark_ext_view(ViewId, ExtViewKind)`), guarded by a table version check, so an older engine just skips it. Acceptance: Bitwarden's popup lays out at its own 380 px.

## Extensions P4: permission requests answered in wubble's UI (`ext-permission-prompts`)

Key: `ext-permission-prompts` · engine patch: yes: waits for the one engine build · state: not written.

In Chrome, `chrome.permissions.request` (with a user gesture) shows a dialog listing the new permissions and resolves true or false. Optional host permissions use the same path, and so do `management.uninstallSelf({showConfirmDialog})` and the re-enable prompt after a permission increase. In wubble, `permissions.request` rejects with "Could not find an active window." (Bitwarden's first-run step; docs/research/extensions.md gap 3; TODO M6 P4). Chromium-side patch, `patches/chromium/50-cef-permission-prompts.patch` (CEF side) and `51-src-permission-prompts.patch`: in `chrome/browser/extensions/api/permissions/permissions_api.cc` (`PermissionsRequestFunction::Run`) and `extension_install_prompt.cc`, under `BUILDFLAG(ENABLE_CEF)`, when the web contents has no `Browser`, call a new delegate entry `permission_prompt(ctx, request_id, extension_id, kind, json_permissions)` in `cef_wubble_ext_delegate_t`. The answer comes through a new table function `permission_answered(request_id, allow)`, which runs the prompt's done callback (`ExtensionInstallPrompt::DoneCallback` with `Result::ACCEPTED`/`USER_CANCELED`). Bump the table to `cef_wubble_ext_v2` with a `size` check, so a v1 engine keeps working. wubble side: `crates/wubble-engine/src/ext_api.rs` adds `ExtRequest::PermissionPrompt { id, extension, kind, permissions }` and `Engine::answer_permission`. Core: reuse `extensions/shell.rs::Prompt` and `prompt_transition` with a new `Prompt::Asking { request, lines }` variant. The words come from the existing `permission_lines`, plus host patterns phrased as Chrome phrases them (`IDS_EXTENSION_PROMPT_WARNING_HOST_*`). Host: `host/ext_ui.rs` shows the same modal kit sheet as the install prompt (Allow / Deny). Granted optional permissions are added to `Extension::permissions` for the Settings list. Uninstall-self confirmation uses the same sheet.

## Extensions: site access controls (on click, on specific sites, on all sites) (`ext-site-access`)

Key: `ext-site-access` · engine patch: yes: waits for the one engine build · state: not written.

Core: a pure `extensions::access` module that maps the stored per-extension mode and site list to what to tell the engine at start and on change, with tests. UI: a per-extension "Site access" kit select in the Settings extensions section, and, in the footer popover (`extensions/shell.rs::Panel`), a per-row badge and an "Allow on this site" row for the visible tab's origin. Store the choice in the installed list (`Extension` gains `site_access`).

## Extensions: install, enable, disable, remove and reload without a restart (`ext-live-management`)

Key: `ext-live-management` · engine patch: yes: waits for the one engine build · state: not written.

In Chrome, installing, toggling, removing and reloading (developer mode's Reload button) take effect at once. wubble applies every change at the next start, because the list becomes `--load-extension` (`wubble_core::extensions` module docs, `engine/app.rs::extension_switches`), and the TODO M6 "install page's restart to apply" is open. Patch `54-cef-ext-management.patch`: add table functions `load_unpacked(profile_path, dir) -> request id`, answered by a delegate `loaded(request_id, extension_id, error)`; `set_enabled(profile_path, extension_id, bool)`; `unload(profile_path, extension_id)`; and `reload(extension_id)`. They are implemented over `extensions::UnpackedInstaller::Create(...)->Load`, `ExtensionRegistrar::EnableExtension`/`DisableExtension(..., disable_reason::DISABLE_USER_ACTION)`, `ExtensionRegistrar::RemoveExtension`, and `ExtensionService::ReloadExtension`, for each loaded profile (each container's request context). Also add `set_file_access(ext_id, bool)` (`util::SetAllowFileAccess`) for Chrome's "Allow access to file URLs". When the extension system was off at start (no extension installed, so `disable-extensions`), live install still needs a restart; keep the restart notice for that case only. wubble side: `ext_api.rs` wrappers, `ExtRequest::Loaded`. Core: an `extensions::apply` pure transition from (running set, desired `Installed`) to effects (Load, Enable, Disable, Unload), with tests. `crates/wubble/src/extensions.rs::change` emits them when `ext_api::available()`, and `unused_copies` deletion waits until an unload is confirmed. UI: Settings rows get a Reload button for unpacked sources and an "Allow access to file URLs" toggle.

## Extensions: allow per container and in agent sessions (Chrome's 'Allow in Incognito') (`ext-container-access`)

Key: `ext-container-access` · engine patch: yes: waits for the one engine build · state: not written.

Chrome loads extensions in incognito only when the user ticks "Allow in Incognito" on the details page (`util::SetIsIncognitoEnabled`). wubble has no private windows. Its isolated contexts are containers, including the ones agent sessions create, and every extension loads in every container (decision "Extensions on"). So a password manager or content script runs inside agent-session tabs too. To build, as the analogue: (1) Core: `Extension` gains `containers: ContainerAccess { All, DefaultOnly, Listed(Vec<ContainerId>) }`, plus `in_agent_sessions: bool` (default false, as Chrome's incognito default is off). Serialise both in `to_json`/`from_json`. A pure `extensions::enabled_in(ext, container, is_agent) -> bool` gets tests. (2) Engine: patch (extends ext-live-management's table) `set_enabled_in_profile(profile_path, ext_id, bool)`, implemented with `ExtensionRegistrar::DisableExtension` and a wubble disable reason on that profile only. wubble calls it when a container's request context is created (`wubble-engine/src/app.rs`, where containers get their profile path) and when the setting changes. Without the patch, an agent container's request context could be made with `--disable-extensions`-equivalent... it cannot, so without the patch the toggle is hidden (`ext_api::available()`). (3) Projection: `extensions/projection.rs::project` leaves out tabs of containers where the extension is off. (4) UI: on each Settings extension row, a kit toggle "Allow in agent sessions" and a kit select "Containers".

Chrome installs from chromewebstore.google.com ("Add to Chrome" through `chrome.webstorePrivate`) and checks the update URL every few hours. wubble installs only from the user's files, with no Web Store and no updates (decisions "Extension install" and "Extension updates"; TODO M6 "install from the Web Store"). To build, all behind a new Bool setting `extensions.web_store` (default 0, `Section::Privacy`, label stating it contacts Google): (1) On chromewebstore.google.com pages, a document script (`View::set_document_scripts`) defines a `chrome.webstorePrivate` shim, ported from samuelmaddock/electron-browser-shell `electron-chrome-web-store` (MIT, with a THIRD_PARTY_NOTICES entry): `beginInstallWithManifest3`, `completeInstall`, `getExtensionStatus` and `isInIncognitoMode` answered from wubble's list. (4) Updates: a pure `extensions::update` state machine (Idle, Checking, Downloading, Ready) driving a daily omaha `update2/crx` check for store-sourced entries. A new `Source::WebStore` keeps the update URL. Tests for the shim's answers and the update machine.

## Extensions: keyboard shortcuts (chrome.commands) and the shortcuts page (`ext-commands`)

Key: `ext-commands` · engine patch: yes: waits for the one engine build · state: not written.

Chrome reads manifest `commands` (`suggested_key` per platform, `_execute_action`, named commands, `global`). chrome://extensions/shortcuts lets the user set or clear each one, a chord fires `commands.onCommand(name, tab)`, and `_execute_action` opens the action popup. wubble has none. Core (pure, tested): `parse_manifest` reads `commands` into `Vec<ExtCommand { name, description, suggested: Option<Chord> }>`, with chord syntax per Chromium `extensions/common/command.cc` (`ParseImpl`: Ctrl/Alt/Shift/Command/MacCtrl plus a key; at most 4 suggested per extension; Ctrl+Alt refused). Bindings live in the keymap. `wubble_core::keys` gets a binding target `Target::Extension { id, command }` alongside `Action`, so conflicts with shell chords are detected by the existing conflict rules and shown in the shortcut editor. Engine patch `55-cef-ext-commands.patch`: table function `command_fire(extension_id, command_name, browser_id)`, which dispatches `commands.onCommand` through `extensions::EventRouter::DispatchEventToExtension`, with the tab object from the wubble registry. It also grants activeTab as `ExtensionKeybindingRegistry::ExecuteCommand` does. A second function `commands_updated(extension_id, json)` lets `commands.getAll` return wubble's bindings (via `CommandService` prefs). `_execute_action` needs no patch: it uses the existing `host/ext_ui.rs::extension_pressed`. `_execute_side_panel` goes to the side-panel feature. Host: the key path (`crates/wubble/src/input.rs`/`bind.rs`) resolves extension targets PageFirst. UI: a "Keyboard shortcuts" block in the Settings extensions section, reusing the shortcut editor's kit rows.

## Extensions: chrome.omnibox keyword mode in the command bar (`ext-omnibox`)

Key: `ext-omnibox` · engine patch: yes: waits for the one engine build · state: not written.

In Chrome, an extension declares `omnibox.keyword`. Typing the keyword followed by Tab or Space enters keyword mode ("<Extension name> |"). `onInputStarted`, `onInputChanged(text, suggest)`, `onInputEntered(text, disposition)`, `onInputCancelled` and `onDeleteSuggestion` fire, and suggestions with description markup (`<match>`, `<dim>`, `<url>`) plus `setDefaultSuggestion` appear as results. wubble's command bar (`wubble_core::omnibox`, `suggest.rs`, `crates/wubble/src/bar.rs`) has no extension source. Core (pure, tested): `parse_manifest` reads `omnibox.keyword`. `omnibox::classify` recognises `<keyword><space>` against the enabled extensions' keywords and yields a `Mode::ExtensionKeyword { ext, text }`. A small state machine `omnibox::ext_session` (Idle, Started, Waiting(req id), Shown) turns typing into effects: Start, Changed(text, req), Entered(text, disposition), Cancelled. Description markup is parsed into styled runs for the kit result row (`ExtensionSuggestion` mapped onto an existing `CommandKind`). Patch `58-src-omnibox.patch`: table functions `omnibox_started(profile, ext)`, `omnibox_changed(profile, ext, text, req)`, `omnibox_entered(profile, ext, text, disposition)`, `omnibox_cancelled(profile, ext)` and `omnibox_delete(profile, ext, content)`, calling `ExtensionOmniboxEventRouter::On*` (`chrome/browser/extensions/api/omnibox/omnibox_api.cc`). A delegate `omnibox_suggestions(ext, req, json)` is fed from `OmniboxAPI`'s suggestions-ready path and `OmniboxSetDefaultSuggestionFunction`. Entered with disposition current tab, new foreground tab or new background tab maps to the extension's own handling, since the extension navigates itself.

## Extensions: the missing tabs/windows events, bounds and windows.create (`ext-tabs-windows-events`)

Key: `ext-tabs-windows-events` · engine patch: yes: waits for the one engine build · state: not written.

Chrome sends `tabs.onMoved`, `onAttached`, `onDetached`, `onReplaced` (a discarded tab coming back), `onHighlighted`, `onZoomChange`, and `windows.onCreated`/`onRemoved`/`onBoundsChanged`.
