## Prompt for every permission CEF 156 forwards (protocol handler, window management, file editing, downloads, local network, sensors, ...) (`perm-kinds-complete`)

Key: `perm-kinds-complete` · engine patch: no · state: not written.

Chrome prompts for many permission types, and CEF 156 forwards all of them to OnShowPermissionPrompt (include/internal/cef_types.h, cef_permission_request_types_t). welding decodes only 12 bits (vendor/welding/src/permissions.rs `decode`). Every other bit arrives as PermissionKind::Other, and wubble denies it silently (crates/wubble/src/prompt.rs `permission_of` returns None). That rejects these APIs with no prompt: showSaveFilePicker/FileSystemHandle.requestPermission write access (FILE_SYSTEM_ACCESS 1<<24), automatic multiple downloads (MULTIPLE_DOWNLOADS 1<<14), getScreenDetails/window placement (WINDOW_MANAGEMENT 1<<23), camera pan-tilt-zoom (1<<1), Captured Surface Control (1<<3), top-level storage access (1<<5), the legacy quota prompt (DISK_QUOTA 1<<6), local network and loopback access (1<<25..27, Chrome's LNA prompt), sensors (1<<28), web app installation (1<<22), FedCM identity provider and ambient login (1<<10, 1<<29), and AR/VR/hand tracking (1<<0, 1<<9, 1<<21).
Add these as named PermissionKind variants in welding (a `wubble change`, with an entry in WUBBLE_CHANGES.md) and as matching wubble_core::site::Permission variants. Each variant gets a stable `as_str`, an entry in Permission::ALL, and an `ask_text` taken from Chromium's permission_request.cc strings, e.g. "Edit files", "Download multiple files", "Manage windows on all your displays", "Look for and connect to any device on your local network", "Use your motion sensors". Map them in prompt.rs `permission_of`. Keep AR/VR/hand tracking and identity provider explicitly denied, with a comment, because no XR runtime or FedCM UI exists. The unit tests in prompt.rs (`every_engine_kind_maps_or_is_never_prompted`) and site.rs need updating. The Settings Sites list (wubble_core::pages::sites_view) shows the new kinds without further work. No new kit pieces are needed: the existing prompt (kit overlay/a/a-prompt.slint via host/surfaces.rs `permission_view`) shows them.

## getDisplayMedia: ask to share the screen, then show a sharing bar with Stop (`screen-share`)

Key: `screen-share` · engine patch: no · state: not written.

In Chrome, getDisplayMedia opens a picker, and while capture runs a bar says "<site> is sharing your screen" with Stop sharing and Hide. In wubble, welding decodes the desktop bits (DesktopAudioCapture, DesktopVideoCapture from decode_media), but prompt.rs `permission_of` maps both to None, so every getDisplayMedia is denied. CEF's media_access_query.cc grants the full primary screen (or the id the page asked for), plus "loopback" system audio when desktop audio is requested. On Linux Wayland, Chromium's PipeWire capturer shows the desktop portal's own source picker after the grant.
Build: (1) Add Permission::ScreenCapture to wubble_core::site, with ask_text "See your screen" (Chromium's string) and an optional system-audio line. Never remember an Allow for it: Chrome asks every time, so the prompt shows no remember toggle for this kind. (2) Map DesktopVideoCapture/DesktopAudioCapture to it in prompt.rs. (3) Start a sharing indicator from the grant. It ends when the page's track stops: extend wubble-helper/src/probes.js, which already reports `capture`, to say `display` separately. It also ends when the tab closes or navigates. The indicator is a kit notice in the pane (overlay/a/a-capsule-bar.slint or a-toast.slint as a derived piece, listed on docs/fidelity/derived-review.md) reading "<site> is sharing your screen", with a "Stop sharing" button and a "Hide" button. Stop runs a page script through View::eval that stops every live display track (the probe keeps a WeakRef list of MediaStreamTracks with displaySurface settings). (4) Agent tabs keep denying, as decided.

## Web notifications shown by wubble, with click-to-tab (`web-notifications`)

Key: `web-notifications` · engine patch: no · state: not written.

In Chrome, once a site is allowed, new Notification() and registration.showNotification() show OS notifications. A click focuses the window, selects the tab and fires the click event. wubble grants the Notifications permission (prompt.rs), but display depends on Chromium's NotificationPlatformBridge inside CEF: on macOS it needs Chrome's alerts helper app, which is not in the bundle. Clicks call WebContentsDelegate::ActivateContents, which Alloy leaves empty, so the tab is never brought forward.
Build repo-side: (1) Add a main-world content script channel `notify` to wubble-helper/src (registered in main.rs `compose`). For a granted origin it replaces window.Notification and ServiceWorkerRegistration.prototype.showNotification from page contexts with a shim. The shim keeps the API shape (permission, requestPermission → the real one, onclick/onclose/onshow, close(), tag replacement, silent, requireInteraction) and posts {id, title, body, icon, tag} to the browser. (2) On the browser side, show the notification in crates/wubble through the `notify-rust` crate (MIT/Apache-2.0; DBus org.freedesktop.Notifications on Linux, the native centre on macOS, toast on Windows), with a THIRD_PARTY_NOTICES entry. On click, raise the window, select the tab and send `click id` back to the shim, which dispatches onclick. Close and replace work the same way. (3) A click on a registration notification focuses the tab and calls the page's notificationclick-equivalent listener only when the page registered one through the shim. Worker-initiated notifications stay Chromium's (push needs FCM, which stays off). (4) Add a Settings row "Show notifications from sites". Icons are fetched only for already-loaded page resources.

## A working location provider for navigator.geolocation (`geolocation-provider`)

Key: `geolocation-provider` · engine patch: no · state: not written.

In Chrome, a geolocation grant gets a position from the OS provider (Core Location on macOS, Windows Location) or from Google's network provider, which needs an API key. wubble prompts for and grants Geolocation (prompt.rs, site.rs), but CEF has no Google API key. Linux has no system provider in Chromium, so pages get POSITION_UNAVAILABLE. On macOS the bundle needs NSLocationUsageDescription for Core Location to ask at all.
Build: (1) On Linux, add a provider module in crates/wubble (behind a trait with one implementation per OS, per AGENTS.md) that reads GeoClue2 over DBus (the `zbus` crate, MIT). While a tab with a granted geolocation is watching, apply the position to that tab through DevTools Emulation.setGeolocationOverride {latitude, longitude, accuracy} (wubble-engine cdp.rs and View's DevTools call path), and clear it when the grant is revoked or the tab navigates cross-origin. To know when a page is watching, add a small `geo` content-script channel that reports getCurrentPosition/watchPosition calls. (2) On macOS, add NSLocationWhenInUseUsageDescription to the app's Info.plist (scripts/release packaging and docs/macos.md) so Chromium's own Core Location provider works. (3) GeoClue may ask a network service for Wi-Fi positioning, so add a setting "Use the system location service for sites", off by default as the no-phone-home rule requires. With it off, the prompt still works and the page gets an error. (4) Unit-test the pure part (grant plus watch state → override or clear effects) in wubble-core.

## navigator.registerProtocolHandler and the handlers list (`protocol-handlers`)

Key: `protocol-handlers` · engine patch: no · state: not written.

In Chrome, navigator.registerProtocolHandler('mailto' | 'web+foo', 'https://site/?u=%s') asks "Allow <site> to open all mailto links?". Later navigations to that scheme go to the site's URL, and Settings → Protocol handlers lists the handlers and the default per scheme. CEF delivers REGISTER_PROTOCOL_HANDLER (1<<19) as a prompt bit, but AlloyBrowserHostImpl does not override WebContentsDelegate::RegisterProtocolHandler, so the call does nothing. wubble hands every unknown scheme to the OS (wubble_core::external, host/external.rs).
Build: (1) Add a main-world content-script channel `protocol` (wubble-helper/src, main.rs `compose`). It wraps navigator.registerProtocolHandler and unregisterProtocolHandler, validates them as the HTML spec does (safelisted schemes or web+, https URL of the same origin, containing %s), and posts them to the browser. (2) Add a pure table in wubble-core (scheme → handlers, default) with transitions and tests. Ask through the existing permission prompt as a new Permission::ProtocolHandler (wording from Chromium's register_protocol_handler_permission_request.cc), and persist the table in persist.rs. (3) In host/external.rs and engine nav (PageEvent::ExternalProtocol / NavigationRefused), a scheme with a default handler is rewritten to the handler URL (the %s filled with the encoded URL) and opened in the tab, before the OS question. The denied-scheme list still applies. (4) Add a Settings Sites subsection "Protocol handlers" with the default per scheme (kit Select) and Delete.
