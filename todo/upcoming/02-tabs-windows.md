## How features are built (owner, standing rule)
Written without compile and test, one branch per feature (`feat/<key>`). Then an integration pass per feature:
compile, test, caveman review then adversarial review, merge. "1 feature gets integrated at once", grouped by
feature, never by individual commit. Batch 1's written branches are integrated this way, one feature at a time
(their reports: [batch-1-reports.md](batch-1-reports.md)). A feature marked "waits for the one engine build" ships
after it ([01-optimization.md](01-optimization.md)).

Default browser is in [13-release-updater-site.md](13-release-updater-site.md).

## Multiple profiles, guest profile and a profile switcher (`multiple-profiles`)

Key: `multiple-profiles` · engine patch: no · state: written on `feat/multiple-profiles`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome: several profiles, each with its own history, bookmarks, passwords, settings and cookies. A profile menu and picker (Ctrl+Shift+M) opens a window of another profile, a Guest profile is thrown away on close, and `--profile-directory=Name` chooses one. Today wubble has one profile per process, chosen only by `--profile DIR` (crates/wubble/src/profile.rs `Profile::resolve`). The instance socket is already per profile (crates/wubble/src/instance.rs). CEF's `root_cache_path` is process-wide, so each profile runs as its own wubble process. Build: a pure `wubble_core::profiles` module covering the list, names, tint, last used, the default profile and the picker choice, with unit tests. It is stored in one small `profiles.json` in the per-user data dir (`app::user_data_dir`), not in any profile's database. The default profile stays at today's directory so nothing migrates. New profiles go in `<data>/Profiles/<id>`. Opening another profile spawns `current_exe --profile <dir>`, or forwards `Message::Focus` to its live instance. Guest: `--guest` makes a fresh profile under `~/Dev`-independent user data (`<data>/Guest`), never in /tmp, and deletes it at exit and again at the next start. Add a Settings section 'Profiles' (settings.rs `Section`, settings page in wubble-ui) to add, rename, delete (with a confirm) and open profiles. Add a command-bar entry and `Action::SwitchProfile` on Ctrl+Shift+M (Cmd+Shift+M), which opens the picker sheet. The profile name goes in the window title and in a small sidebar footer mark (derived kit piece). The picker at start is shown only when the 'Show on startup' setting is on.

## Capture each tab's back/forward entries, and the back button history menu (`nav-history-capture`)

Key: `nav-history-capture` · engine patch: no · state: written on `feat/nav-history-capture`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome keeps every tab's navigation stack (URL, title, index). It shows the stack on right-click or long-press of back and forward, and Ctrl/middle-click on back opens that entry in a new tab. Session restore, reopen closed tab and duplicate all carry the stack. Today wubble keeps only `Tab::url`, and nothing reads navigation entries (TODO: 'Undo close tab ... bring back the URL only'). Build the capture half. Read the stack after each committed navigation and before a close or discard. Use `CefBrowserHost::GetNavigationEntries` with a visitor in crates/wubble-engine (nav.rs or view.rs), or CDP `Page.getNavigationHistory` through cdp.rs, reported as a new page event. Keep it in a host-side table keyed by TabId (one owner, out of `Model` so model saves stay cheap), capped at Chromium's 50 entries (`kMaxPersistNavigationCount`). Persist it in wubble-store with a migration: a `tab_history` table (tab id, index, url, title) written with the session, and the same columns for `recently_closed` rows (crates/wubble-store/src/closed.rs `ClosedTab` gains `entries` and `index`). Skip agent and private tabs. UI: right-click or press-and-hold on the back and forward lights (`.wb-nav`) opens a kit menu of entries (`menu.rs` entries style, like `tab_entries`). Choosing one calls CDP `Page.navigateToHistoryEntry` or GoBack/GoForward n times. Ctrl/middle-click on back or forward opens that entry in a background tab. A 'Show full history' row opens wubble://history.

## Recently closed windows, folders and Spaces, and a recently-closed list UI (`recently-closed-full`)

Key: `recently-closed-full` · engine patch: no · state: written on `feat/recently-closed-full`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome's TabRestoreService keeps tabs, whole windows and tab groups. Ctrl+Shift+T reopens the newest entry of any kind, and the History menu and tab search list 'Recently closed' with titles. Today crates/wubble-core/src/closed.rs and wubble-store/src/closed.rs keep tab entries only, and nothing lists them (`Store::recently_closed` has no caller in crates/wubble). A closed Main window keeps its Space, so it is not remembered at all (model/windows.rs close_window), and a closed folder or deleted Space adds its tabs one by one, if at all. Build: generalize the store row into an entry enum, `Tab | Window { space, geometry } | Folder { name, tabs } | Space { name, tint, icon, container, tabs }`, with a migration. Grouped entries carry child tab rows with url, title, container, place and, once captured, history. Record a Window entry in `close_window` (and a Space entry from `DeleteSpace` and `FolderRow::Close`, when they actually close tabs). Extend the `closed::Event` and `Effect` machine: `Restore` gains a window variant (reopen a Main window on that Space at its geometry, or recreate the Space if it is gone) and a folder or Space variant. Mod+Shift+T and Mod+Z pop any kind. UI: a 'Recently closed' block at the top of wubble://history (pages.rs, history page model), and command-bar rows (bar.rs) listing the entries with titles. Each row reopens its entry and can be deleted on its own. Keep RECENTLY_CLOSED_MAX at 25 entries. Agent and private tabs stay off the list.

## Startup, home page and quit settings (`startup-home-settings`)

Key: `startup-home-settings` · engine patch: no · state: written on `feat/startup-home-settings`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome's 'On startup' setting offers: open the New Tab page, continue where you left off, or open a specific set of pages. There is a Home page (Alt+Home / Cmd+Shift+H), a 'Restore pages?' offer after a crash, and on macOS 'Warn before quitting'. The design's settings (pages/settings.tsx row `startup`: 'When Wubble opens', Start page | Last session) have the first two. wubble has no such setting: it always restores the stored session (wubble-store session.rs load_session). Build: settings rows in crates/wubble-core/src/settings.rs. `startup.mode` is a Select of Last session (default), Start page, or Specific pages. `startup.pages` is a list editor of URLs, shown only for Specific pages. `home.url` is empty for the start page. `quit.warn` (macOS default on) requires a second Cmd+Q or a hold. At start, in crates/wubble/src (where the loaded Model is handed to the host): with Start page, keep Spaces, pinned tabs and folders, but open a start tab in each window. The unpinned tabs of the last session go to the archive or recently closed, following Chrome's 'new tab page' semantics: they are not restored. Pinned tabs always stay. With Specific pages, open those pages as new tabs. Record a clean-exit flag in the store. When the last run did not exit cleanly and the mode is not Last session, show a kit banner 'Restore pages?' that restores the saved session. Add `Action::GoHome` (Alt+Home on Linux/Windows, Cmd+Shift+H on macOS) and a palette title 'Home'. Add a command-bar row 'Open pages from last session'.

## Tab tear-off: new window at the drop point, drop into a window at a row (`tear-off-fidelity`)

Key: `tear-off-fidelity` · engine patch: no · state: written on `feat/tear-off-fidelity`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome: a tab dragged out of the strip becomes a live window following the pointer. Released, it stays where it was dropped, at the source window's size. Dropped onto another window's strip, it goes in at the hovered position. wubble's `tabdrag` machine (crates/wubble-core/src/tabdrag.rs) decides `Effect::MoveToWindow { to: WindowTarget::New | Existing }`. But `Model::move_tab_to_window` (model/windows.rs) creates the new window with `geometry: None` (the platform default place and size), and always puts the tab last (`index: usize::MAX`) in the target Space. Build: carry the drop point and the source window's size into `WindowTarget::New { geometry }` and `Geometry.pos` on X11, macOS and Windows, so the window opens under the pointer, offset by the grab point within the row. For `Existing(w)`, hit-test the target window's tab list: add `list` rects of other windows to `Targets.windows` in crates/wubble/src/host/tab_drag.rs `other_windows`. Pass a `Dest` (pinned, normal or folder index) so the tab lands at the hovered row, and the target window's rows show the gap while hovering (`tabs::TabRows`). Also move whole folders and split groups when their header or a split pane is dragged out (Chrome moves a whole group). Unit tests go in tabdrag.rs and model/tests.rs. On Wayland positions stay unknown: see wayland-tab-drag.

## Wayland: drag tabs between windows and live tear-off via the data device (`wayland-tab-drag`)

Key: `wayland-tab-drag` · engine patch: no · state: written on `feat/wayland-tab-drag`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome on Wayland drags tabs between windows with a real wl_data_device drag. With `xdg_toplevel_drag_v1` (KWin, Mutter 46+, wlroots) the torn-off window itself follows the pointer. wubble cannot do either today. tabdrag.rs states that on Wayland a release outside the window is always `Outside` (a new window), and `other_windows` is empty there. Build: when a tab drag leaves the window on Wayland, start a data-device drag from the platform worker behind the `Aux` trait (crates/wubble/src/wl/wayland.rs, which already does drags out, `drag_file.rs`) with a private MIME type `application/x-wubble-tab` carrying the profile's instance id and the TabId. Every wubble window's surface already receives data-device enter, motion and drop. Map an offer of that type to `DropTarget::Window(id)` with a local point, and feed motion into the tabdrag machine of the target window so its list shows the gap. Drop then runs `MoveTabToWindow { Existing }` with the row from tear-off-fidelity. If the compositor advertises `xdg_toplevel_drag_manager_v1` (wayland-protocols staging), create the new window at drag start, attach it with `xdg_toplevel_drag_v1.attach` at the grab offset, and move the tab into it at once, so the window travels with the pointer and is placed where it is dropped. Otherwise keep today's open-on-release behaviour. A cancelled drag (Esc, or a drop on another app) returns the tab, or keeps the new window under xdg_toplevel_drag. Refuse offers from another profile or process.

## Select several tabs (Ctrl/Shift+click) and act on the selection (`multi-select-tabs`)

Key: `multi-select-tabs` · engine patch: no · state: written on `feat/multi-select-tabs`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome: Ctrl/Cmd+click adds a tab to the selection, Shift+click selects a range. The tab menu then acts on all selected tabs: close, pin, mute, move to a new window, add to a group, reload, duplicate, bookmark. Dragging moves them together. wubble has `Command::CloseTabs(Vec<TabId>)` but no selection: Shift+click on a tab row is the peek (`Glance`) and Ctrl+click is a background tab only for links. Build: a pure selection state in wubble-core (a new `tabselect` module or inside `tabs`), owned once: the anchor and the set, cleared on activation of an unselected tab, on a Space switch and when tabs close. Unit tests come with it. The tab row (kit/chrome/tab-row.slint) reports the modifiers on press (a callback argument, no new drawing). The selected look uses the row's existing hover or selected state from the kit, or a derived piece put on the review sheet. In crates/wubble-core/src/tabmenu.rs `entries` takes the selection: labels read 'Close 3 tabs', 'Pin tabs', 'Move tabs to new window', 'New folder with 3 tabs', 'Mute tabs', and `Run` gets list variants that the host maps to one Command each (CloseTabs, a new PinTabs/MoveTabs/FolderWithTabs). Dragging a selected row moves the whole selection in order through tabdrag (reorder, onto a Space, into a split edge with exactly two, tear-out). Pinned and normal tabs are kept apart, as Chrome does. Escape clears the selection.

## Tab search (Ctrl+Shift+A): all open and recently closed tabs in one list (`tab-search`)

Key: `tab-search` · engine patch: no · state: written on `feat/tab-search`, awaiting integration (its report: [batch-1-reports.md](batch-1-reports.md)).

Chrome's Tab Search (Ctrl+Shift+A, Cmd+Shift+A) is a popover that lists every open tab of every window, most recent first, with favicons, titles, sites and a close button per row. Typing filters with the same matcher omnibox uses, so the rows come from one pure function in wubble-core/src/omnibox.rs with tests. Enter or a click runs `Command::ActivateTab` plus a window focus or Space switch for a tab of another Space (reuse `Target::OpenTab`). A per-row close (kit list row's trailing button, as in the history page rows) closes the tab without leaving the list. Up/Down and Delete work from the keyboard.
