## Docked DevTools without the remote debugging port (embedder bridge) (`devtools-pipe-bridge`)

Key: `devtools-pipe-bridge` · engine patch: no · state: not written.

Chrome docks DevTools by default and serves the frontend over an in-process pipe; nothing listens on TCP. In wubble, docking only works while `devtools.remote_port` is set (`wubble_core::devtools::Mode::of`, `settings::DEVTOOLS_REMOTE_PORT`): by default DevTools is detached-only, and the setting's own warning says any local program can then drive every tab. Build a host-owned bridge instead. Load the bundled frontend (`devtools://devtools/bundled/devtools_app.html`, or `inspector.html` from CEF's resources) in the panel view that `crates/wubble/src/host/devtools.rs::open_panel` already opens. Before its scripts run, a document script (`View::set_document_scripts`, `cdp::DocScripts`) defines `window.InspectorFrontendHost` with `sendMessageToBackend`, which calls a `Runtime.addBinding` binding on the frontend view. The host reads `Runtime.bindingCalled` from the panel view's CDP events and forwards each message with `View::cdp`-style raw sends on the inspected tab's DevTools channel (welding `send_devtools_message`). The inspected tab's `on_dev_tools_message` traffic for that session goes back through `View::eval` as `DevToolsAPI.dispatchMessage(...)`. Add an engine API for raw passthrough (`View::devtools_raw_send`, plus a `PageEvent::DevToolsRaw` that a session tag separates from wubble's own `CdpId` replies), so wubble's own calls and the frontend's ids never collide (rewrite ids with an offset). Implement the host methods the frontend needs: `getPreferences`/`setPreference`/`removePreference`, stored as JSON in the profile; `openInNewTab` (the existing `new_tab`); `copyText` (clipboard.rs); `save`/`append` (the save chooser); `bringToFront`; `closeWindow`; `inspectedURLChanged`; `setIsDocked`/`requestSetDockSide`, handed to the dock-sides feature; `loadNetworkResource` through `wubble-engine/src/fetch.rs`. In `wubble_core::devtools`, `Mode::Docked` no longer needs a port: `frontend_url` becomes the bundled URL, and `AskTarget` is only needed for the HTTP path. Keep the port path as a fallback. Unit tests for the id rewriting and the new transition rows go in `wubble-core`.

## DevTools dock positions: right, bottom, left, undocked (`devtools-dock-sides`)

Key: `devtools-dock-sides` · engine patch: no · state: not written.

Chrome's DevTools menu (the three-dot menu, then Dock side) offers dock to right, bottom, left, or undock into a separate window. It remembers the choice per profile, and Ctrl+Shift+D cycles through the positions. wubble docks only at the right edge (`host/devtools.rs`: the `PANEL_TAB` pane, with the `SourceSeam` width from `wubble_core::split::SourceSeam`). Detached means CEF's own native window (`View::open_devtools_at`), which is not a wubble window. TODO M4 lists the bottom dock as needing vertical pane rects. To build: (1) In `wubble-core`, add a `DockSide` enum {Right, Bottom, Left, Undocked} to `devtools::Dock::Open { tab, side }`, and add `DockEvent::SetSide(DockSide)` and `CycleSide` with pure transitions and tests. Persist the side as a hidden setting `devtools.dock_side` (`settings.rs`, `Section::Hidden`). (2) Pane geometry: extend `crates/wubble/src/panes.rs` and `host/panes.rs::pane_layout`/`layout_panes` so the panel can take a horizontal strip at the bottom, with a height seam. `SourceSeam` gets an axis, or a second seam instance owned by `Docked`. (3) Undocked: open a wubble window of a new `WindowKind::DevTools` (`wubble_core::window`) that shows only the panel view, so it works on Wayland and composes with the shell. Its close sends `DockEvent::PanelClosed`. CEF's native window stays only for the no-bridge fallback. (4) The frontend's `requestSetDockSide`/`setIsDocked` (from devtools-pipe-bridge) drive `SetSide`, and the frontend is told the current side through `DevToolsAPI.setDockSide`. (5) Add an `Action::DevToolsCycleDock` with the chord Ctrl+Shift+D (Cmd+Shift+D on Mac) in `keys.rs`, PageFirst, active only while the panel has focus. UI: any new seam handle comes from kit components. Shoot the bottom dock and the undocked window with `--shot`.

## Inspect-at-point, Console and element picker in the docked panel (`devtools-inspect-docked`)

Key: `devtools-inspect-docked` · engine patch: no · state: not written.

In Chrome, the context menu's Inspect opens DevTools docked with the node under the pointer selected. Ctrl+Shift+J opens the Console, and Ctrl+Shift+C opens Elements in element-picker mode. In wubble, `DockEvent::InspectAt` always closes the docked panel and opens CEF's detached window (`wubble_core::devtools::transition`, comment "native-window only"; TODO M4 "Inspect-at-point in the docked panel"). There is also no Console or picker chord (`keys.rs` binds only F12, Ctrl+Shift+I and Cmd+Alt+I to `Action::DevTools`). To build, on top of devtools-pipe-bridge: (1) `InspectAt(tab, point)` opens or keeps the docked panel and emits a new `DockEffect::RevealAt { tab, point }`. (2) The host executes it on the inspected tab's CDP: `DOM.enable` if needed, then `DOM.getNodeForLocation {x, y, includeUserAgentShadowDOM: false}` → `backendNodeId`. The id goes into the frontend's message stream as the event `Overlay.inspectNodeRequested {backendNodeId}`, through the bridge's dispatch, which makes the frontend reveal the node in Elements. A frame's point needs `Page.getFrameTree` and the frame's offset; use the frame id that the context menu already carries (`frame_id`, welding change 42). (3) Add `Action::DevToolsConsole` (Ctrl+Shift+J, Cmd+Alt+J) and `Action::DevToolsInspectElement` (Ctrl+Shift+C, Cmd+Alt+C) in `action.rs`/`keys.rs`, with new `DockEvent::Open(tab, Panel)` rows. On open, the host evaluates `DevToolsAPI.showPanel('console')` or `DevToolsAPI.enterInspectElementMode()` in the frontend view. (4) A press of Inspect while a panel is open for another tab switches the panel to that tab. Add pure tests in `wubble-core/src/devtools.rs`, and update the existing test that expects `OpenDetached` for `InspectAt` in docked mode.

## Remote debugging UI: a wubble://inspect targets page (`remote-debug-inspect-page`)

Key: `remote-debug-inspect-page` · engine patch: no · state: not written.

Chrome has chrome://inspect: lists of pages, extensions, service workers, shared workers and other targets, each with inspect/focus/reload/close. It also has "Discover network targets" with a configurable host:port list (Node at localhost:9229 and so on), "Open dedicated DevTools for Node", and a remote-debugging status section. wubble has only the `devtools.remote_port` Settings row (`settings.rs`, `Section::Privacy`, restart) and no page that lists targets. To build: a new `InternalPage::Inspect` (`wubble_core::pages`, url `wubble://inspect`, a palette entry in `action.rs`), drawn only from kit components in `crates/wubble-ui/ui/` (rows like the Task manager's list). Rows come from the model: tabs, with a pure projection in a new `wubble_core::inspect` module. Extension popups, the DevTools panel and extension service workers come from `Target.getTargets` sent over any open view's CDP channel, or over the browser target that `Target.attachToBrowserTarget` gives. Each row has Inspect, which opens DevTools through `dock_event` for tabs, or a detached frontend attached to the target id for workers (the bridge with a flattened `Target.attachToTarget` session), plus Focus and Close. Show the endpoint's state: port set or off, whether it is bound (the loopback connect check that `open_panel` already does), and a warning line. Network targets: a `devtools.network_targets` List setting (default empty). Each entry is polled at `http://host:port/json/list` through `fetch.rs` only while the page is shown and only when the list is non-empty, so nothing is requested by default. Inspect opens the frontend with `?ws=` pointing at that target's webSocketDebuggerUrl. The state machine for polling goes in core, with tests.

## Screen reader detection on macOS and Windows (`a11y-screen-reader-detect`)

Key: `a11y-screen-reader-detect` · engine patch: no · state: not written.

Chrome turns its accessibility tree on when an assistive technology connects, on every platform. wubble's `a11y.web` auto mode (`wubble_core::apply::web_accessibility`) depends on `crates/wubble/src/screen_reader.rs`, which has a Linux AT-SPI source only. macOS and Windows use `NoReader` (always false), so on auto, VoiceOver and NVDA users get no page content until they find the setting. To build: implement the existing `ScreenReader` trait per platform in `screen_reader.rs`, read off the UI thread the way `os_motion.rs` reads reduced motion. macOS: `NSWorkspace.sharedWorkspace.isVoiceOverEnabled`, observed with KVO (`voiceOverEnabled`) through objc2-app-kit, already a dependency for `mac_app.rs` (check its feature list). Also treat `AXIsProcessTrusted` clients as on, as Chrome's `BrowserAccessibilityStateImplMac` does via `NSApplication accessibilityRequested`/`AXEnhancedUserInterface` (behaviour only). Windows: `SystemParametersInfoW(SPI_GETSCREENREADER)`, polled on the existing watcher cadence, plus the `WM_SETTINGCHANGE`/`SPI_SETSCREENREADER` notice if the event loop exposes it. Add a `windows` crate feature only if needed, compile-checked by CI. The pure decision stays `apply::web_accessibility`. Also make the Settings label of `a11y.web` say auto works on all three platforms.

## Caret browsing (F7) (`a11y-caret-browsing`)

Key: `a11y-caret-browsing` · engine patch: no · state: not written.

Chrome toggles caret browsing with F7, after a confirm dialog ("Turn on caret browsing?" with "Don't ask again"). A movable text caret then appears in page content for keyboard selection. The setting is also in Settings, Accessibility, "Navigate pages with a text cursor" (pref `settings.a11y.caretbrowsing.enabled`, pushed to Blink's `WebPreferences::caret_browsing_enabled` by `ChromeContentBrowserClient::OverrideWebkitPrefs`). wubble has neither. To build: (1) Settings: a Bool `a11y.caret_browsing` (default 0, Accessibility section) and a hidden `a11y.caret_browsing_no_ask`. (2) `wubble_core::action`: `Action::ToggleCaretBrowsing` bound to F7 (all platforms) in `keys.rs`, PageFirst. The first press shows a kit confirm sheet (reuse `controls::confirm`) unless no_ask is set. A pure transition decides ask, toggle or nothing, with tests. (3) Engine: generalise `View::set_minimum_font_size`'s request-context preference code into `View::set_preference(name, Value)` (bool, int, string and list variants) in `crates/wubble-engine/src/view.rs`, and set `settings.a11y.caretbrowsing.enabled` on every container's request context at start and on change, through `wubble_core::apply`'s effect list. If CEF's Alloy-style windowless views do not pick the pref up (check by hand), fall back to DevTools `Emulation`... there is none, so instead send `Page.setWebLifecycleState`... no. In that case, report it as an engine patch needed in `OverrideWebkitPrefs` for Alloy browsers.

## Spell check: Add to dictionary, a toggle, a custom word list and context-menu rows (`spell-menu-settings`)

Key: `spell-menu-settings` · engine patch: no · state: not written.

Chrome's context menu on a misspelled word shows the suggestions, "No spelling suggestions", "Add to dictionary" and a "Spell check" submenu ("Check spelling of text fields", languages, Language settings). Settings has "Spell check" on/off, a language list and "Customize spell check", a list of added words with remove. wubble shows only the suggestions (`crates/wubble/src/menu.rs`, group 0, ids 200-204). It has no Add to dictionary, no toggle and no word list (`settings.rs` has no spell row; decision "English spelling dictionary ships" says none existed). To build: (1) In `menu.rs`, CEF ids `MENU_ID_NO_SPELLING_SUGGESTIONS` (205, disabled row) and `MENU_ID_ADD_TO_DICTIONARY` (206, which CEF executes itself: `AddWordToDictionary`). Add a "Check spelling of text fields" toggle row in editable fields. Update menu tests. (2) Settings: a Bool `spell.enabled` (default 1), applied as pref `browser.enable_spellchecking` through a generalised `View::set_preference` (refactor of `set_minimum_font_size` in `wubble-engine/src/view.rs`) on each container's request context, through `wubble_core::apply`. (3) Custom words: Chromium keeps them in `<profile>/Custom Dictionary.txt`. Add a Settings list (kit list editor, `controls::list_editor`) that reads the file and removes words via `CefBrowserHost::RemoveWordFromDictionary` (welding passthrough on a live view), plus an add field (`AddWordToDictionary`). A pure diff of the list in `wubble_core::spell`, with tests. macOS: the system checker learns words through NSSpellChecker; the same CEF calls apply.

## Spell check in other languages: opt-in dictionary download and language list (`spell-languages-download`)

Key: `spell-languages-download` · engine patch: no · state: not written.

Chrome lets the user pick several spell-check languages (pref `spellcheck.dictionaries`) and downloads each `<lang>-<ver>.bdic` from redirector.gvt1.com. wubble bundles en-US only, Chromium's download host is refused (decision "Chromium's own requests", `host-resolver-rules`), and TODO "Spell check in other languages" asks for an opt-in download. To build: (1) Core (pure, tested): `wubble_core::spell` gains a table of the languages Chromium 156 supports, with their versioned file names, copied from `components/spellcheck/common/spellcheck_common.cc` `kSupportedSpellCheckerLanguages` and the version map in `chrome/browser/spellchecker/spellcheck_hunspell_dictionary.cc` (BSD, with a source comment). Add a `DictState` per language (Absent, Downloading, Ready, Failed) with a transition. `plan` is extended to multiple wanted languages, never deleting a user-wanted file. (2) Settings: a List `spell.languages` (default `["en-US"]`) and a Bool `spell.download` (default 0, `Section::Privacy`, the label naming the host). While the download setting is off, only installed languages can be picked. (3) Download through wubble's own fetch (`crates/wubble-engine/src/fetch.rs`, which goes through CEF's network stack, so pick a host that `host-resolver-rules` allows): `https://chromium.googlesource.com/chromium/deps/hunspell_dictionaries/+/refs/heads/main/<file>?format=TEXT` (base64), or a configurable mirror. Write to `<profile>/Dictionaries` atomically and check the size and a pinned SHA-256 from the table. (4) Apply the list as pref `spellcheck.dictionaries` through `View::set_preference` on each request context. On macOS, the list maps to system languages, so nothing is downloaded and the row says so.
