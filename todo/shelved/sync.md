## Build-out features (2026-11-22)

## Sync engine: end-to-end encrypted, to a folder the user picks, off by default (`sync-core`)

Key: `sync-core` · engine patch: no · state: not written.

Chrome Sync keeps bookmarks, history, passwords, open tabs and settings in step across devices with optional passphrase (end-to-end) encryption. wubble has none (TODO.md "Sync (deferred)"; docs/decisions.md "Sync: Deferred, no design work yet"). The owner wants E2E encryption, a destination the user chooses (folder or WebDAV), off by default, nothing phoning home. Build a new crate `wubble-sync` (pure except its transports): (1) keys: a random 256-bit account key, wrapped by a key derived from the user's passphrase with Argon2id (RustCrypto argon2, MIT/Apache), stored wrapped in the destination (`keys.json`) and unwrapped key cached in the OS keyring (reuse `wubble_vault::KeyRing`); a printable recovery code. (2) Record format: per collection, per record id, an encrypted blob (XChaCha20-Poly1305 or AES-256-GCM with collection+id as associated data), a Lamport/HLC timestamp and device id, tombstones; server-blind (file names are HMACs of ids). (3) Layout: append-only per-device change logs plus periodic compacted snapshots so a folder synced by Syncthing/Dropbox/iCloud Drive never sees write conflicts (each device writes only its own files). (4) Transport trait `Remote { list, get, put, delete }` with `FolderRemote` here. (5) Lifecycle in wubble-core `sync::State` (`Off -> Setup -> Unlocked -> Syncing -> Idle -> Error{retry_at}`, one `transition`, effects executed by the host), device registry record (name, platform, last seen). Merge rules per collection are pluggable (`sync-collections`). Setting `sync.enabled` default false; nothing runs until set up. Unit tests for crypto round trip, wrong passphrase, log merge and compaction.

## Sync collections: bookmarks, history, passwords, addresses, settings, open tabs (`sync-collections`)

Key: `sync-collections` · engine patch: no · state: not written.

With `sync-core` in place, map wubble's data to sync records the way Chrome's data types do. Build: (1) stable ids and change tracking in crates/wubble-store: migration adding a `guid` (random, unique) and `modified_ms` to `bookmarks`, `urls`/`visits` (or a visit guid), `logins`, `addresses` (if present), `settings`, plus a `sync_changes` table (collection, guid, op, at) written in the same transactions that change rows (or derived by comparing `modified_ms` with the last sync mark), and tombstones for deletes. (2) Per-collection adapters implementing a `Collection` trait from wubble-sync: `to_record`/`apply_record`/`merge(local, remote) -> resolution`: bookmarks (tree by parent guid + position, last-writer-wins per field, dedupe of identical url+parent as Firefox Sync does), history (union of visits, capped like Chrome to 90 days), passwords (decrypted on the store thread from wubble-vault and re-encrypted under the sync key only; never plaintext on disk; conflict -> newer `password_modified`), settings (only rows marked syncable in crates/wubble-core/src/settings.rs `SettingDef`, a new `sync: bool` field), Spaces/pinned tabs/open tabs per device as a `tabs` collection (read-only for other devices, feeds `send-tab-to-device`'s "tabs from other devices"). (3) The host applies remote changes through the existing owners (Model for Spaces, store for bookmarks/history, `VaultCommand` for logins) and re-renders. Choose per collection in the sync settings. Unit tests per adapter with merge cases.

## Sync transport: WebDAV (Nextcloud, ownCloud, any DAV server) (`sync-webdav`)

Key: `sync-webdav` · engine patch: no · state: not written.

The owner wants sync to a place the user chooses, such as WebDAV, not a wubble server. Add `WebDavRemote` implementing `sync-core`'s `Remote` trait in crates/wubble-sync: PROPFIND depth 1 for list (parse the multistatus XML with quick-xml, MIT), GET, PUT with `If-Match`/`If-None-Match: *` ETags for safe snapshot replacement, DELETE, MKCOL for the base directory; Basic auth over https only (refuse plain http unless the host is loopback), credentials stored in the OS keyring via `wubble_vault::KeyRing` (a separate account name), never in the settings table; server certificate errors fail closed; timeouts and exponential backoff reported as `sync::State::Error{retry_at}`. HTTP through the workspace's `ureq` 3 dependency on a worker thread, never the UI or CEF IO thread. Requests go only to the URL the user typed and only while `sync.enabled` is on (the no-phone-home rule); add the transport to `net_audit.rs` expectations as an opt-in request so `--smoke data` stays clean on a fresh profile. Unit tests for the PROPFIND parser with Nextcloud and Apache mod_dav fixtures, and a loopback test server in tests is not required (owner: no new tests beyond unit level).

## Sync settings: set up, passphrase, destination, data types, devices (`sync-settings-ui`)

Key: `sync-settings-ui` · engine patch: no · state: not written.

Chrome's "You and Google > Sync" page turns sync on, picks data types, sets an encryption passphrase, and lists devices. wubble needs the equivalent for `sync-core`: build a Settings section (crates/wubble-core/src/settings.rs new `Section::Sync` with `sync.enabled` default false and per-collection toggles bookmarks, history, passwords, addresses, settings, open tabs; rendered by crates/wubble-ui/ui/components/settings.slint) and a setup sheet from kit parts: (1) destination choice: "A folder" (OS folder chooser via `crate::chooser`, `Pick::Folder`) or "WebDAV" (URL, username, password fields), with a Test button; (2) passphrase: create (twice, strength from zxcvbn if `pw-checkup` added it) or, when the destination already holds `keys.json`, enter it to join; show and copy the recovery code once; (3) status row: last synced time, error text from `sync::State::Error`, "Sync now"; (4) devices list from the device registry with rename for this device and "Remove" (writes a tombstone so the removed device stops syncing on its next run); (5) "Turn off and forget" which removes the keyring entries and local sync marks but not data. Host wiring in a new crates/wubble/src/host/sync.rs that owns the `sync::State` and runs effects on a worker thread, with a periodic timer only while enabled (no idle polling when off, respecting the 0-to-2 slint_renders idle rule: status updates must not redraw while hidden). Gallery scenes for each sheet state; derived pieces listed on docs/fidelity/derived-review.md.

## Send tab to your devices, and tabs from other devices, over sync (`send-tab-to-device`)

Key: `send-tab-to-device` · engine patch: no · state: not written.

Chrome's page and tab context menus offer "Send to your devices" (the other device shows a notification/omnibox chip to open it), and History shows "Tabs from other devices". Build on `sync-core`/`sync-collections`: (1) a `sent_tabs` collection: record {id, url, title, from_device, to_device, sent_ms, opened}, encrypted like others, expiring after 10 days (Chrome's TTL), deleted when opened or dismissed; pure merge and expiry logic with unit tests. (2) Sending: a "Send to your devices" row in the tab menu (crates/wubble-core/src/tabmenu.rs `ROWS`, data) and the page context menu (crates/wubble/src/menu.rs), opening a small device picker popover (kit `AMenuPopover` rows with device names from the registry), only shown when sync is on and another device exists; then an immediate sync push. (3) Receiving: on sync pull, a new record for this device shows a toast (crates/wubble-ui/ui/components/toast.slint) "<title> from <device>" with Open (new tab in the current Space) and Dismiss, plus a badge-less entry in the omnibox suggestions list until handled (crates/wubble-core/src/suggest.rs source). (4) Tabs from other devices: a section on the History native page (crates/wubble-ui/ui/components/pages.slint) listing each device's open tabs from the `tabs` collection, click to open. Host in crates/wubble/src/host/sync.rs. Nothing is sent anywhere but the user's own sync destination.
