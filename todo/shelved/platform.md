## macOS: open links and files from other apps, Dock reopen and Dock menu (`macos-open-urls`)

Key: `macos-open-urls` · engine patch: no · state: not written.

On macOS, LaunchServices delivers a clicked link or an "Open With" file as an Apple Event, not as argv. wubble handles neither. `crates/wubble-engine/src/mac_app.rs` overrides only `sendEvent:` and `terminate:`, and `wubble-bundle`'s Info.plist (`crates/wubble-bundle/src/main.rs` `add_plist_keys`) has no `CFBundleURLTypes` or `CFBundleDocumentTypes`, so wubble cannot even be picked as the default browser. To build: (1) in `add_plist_keys`, `CFBundleURLTypes` for http and https (role Viewer) and `CFBundleDocumentTypes` for public.html, public.xhtml, com.adobe.pdf, public.svg-image, public.png/jpeg/gif/webp and public.plain-text, with `LSHandlerRank` Alternate. Chrome's Info.plist is the model. (2) In `mac_app.rs`, from `prepare_process` before `finishLaunching`, register `NSAppleEventManager setEventHandler:` for kInternetEventClass/kAEGetURL ('GURL'). Add `application:openURLs:` (files, `file://`) to winit's application delegate class with `class_addMethod`, as `wl/macos.rs` does for winit's view. (3) Each URL goes to the host as `instance::Message::Open` (the same path a second start takes, `instance::listen`'s `deliver`), queued until the first window's host exists, because a cold start's event comes before it. (4) `applicationShouldHandleReopen:hasVisibleWindows:`: with no visible window, open a main window (Chrome's behaviour). (5) `applicationDockMenu:` with "New Window". The menu is built from the action table, so it runs `Action::NewWindow` through `perform.rs`. Compile-check from Linux only. Run nothing on the Mac.

## macOS: a native menu bar with every command (`macos-menu-bar`)

Key: `macos-menu-bar` · engine patch: no · state: not written.

Chrome on macOS has a full menu bar (app, File, Edit, View, History, Bookmarks, Profiles, Tab, Window, Help) whose items show their shortcuts and run the same commands as the keys. wubble has only winit's default app menu: there is no NSMenu code anywhere, and decisions.md "Edit commands" says Cmd edit forms run as actions because Blink leaves them to the menu. Without a Window menu there is no Cmd+` window cycling, no Window list, and no Services or Emoji & Symbols. To build: (1) a pure table in `wubble-core` (`menubar.rs`) of menus, each item an `Action` (`wubble_core::action`) with its label and enabled rule, its shortcut read from the user's `Keymap` (`wubble_core::keys`), so rebinding updates the menu. Unit-test that every bound action appears. (2) A macOS edge in `crates/wubble/src/menubar_mac.rs` (objc2-app-kit) that builds `NSApp.mainMenu` from the table at start and on keymap changes. Each item's target forwards its `Action` to the focused window's host and runs it as `perform.rs` does. Set `windowsMenu`, `servicesMenu` and `helpMenu` so AppKit adds Window list, Services, Emoji & Symbols and Help search. (3) Key equivalents: AppKit's `performKeyEquivalent:` reaches the menu before winit, so the host must not run a chord twice. Either route Cmd chords to the menu (and drop the host path on macOS for those), or answer `menuHasKeyEquivalent` false while a page or shell field that owns the chord (`Route::PageFirst`) has focus. Pick one rule, put it in decisions-worthy terms in the report, and keep `input.rs` routing tests green. The app menu covers About, Settings (Cmd+,), Hide, Hide Others, Show All and Quit (through the existing `set_quit_handler`). Compile-check only; macOS only.

## macOS: Services and Look Up for page and shell selections (`macos-services`)

Key: `macos-services` · engine patch: no · state: not written.

In Chrome on macOS, the app menu's Services submenu and the context menu's Services offer system services on the selected text (Search with Google, New Note, Add to Music, translate), and Cmd+Ctrl+D / three-finger tap shows Look Up. wubble's page lives in an off-screen CEF view, so AppKit never asks winit's view for a selection. To build: (1) add `validRequestorForSendType:returnType:`, `writeSelectionToPasteboard:types:` and `readSelectionFromPasteboard:` to winit's NSView class at run time (`class_addMethod`, the technique `crates/wubble/src/wl/macos.rs` uses for `draggingEntered:`). They answer for NSPasteboardTypeString when the focused page has a selection. (2) Selection text: welding's OSR `OnTextSelectionChanged` (in `vendor/welding/src/macos_cef/cef_backed.rs`; if it is not forwarded yet, forward it as a `wubble change`) kept per view as the latest selected text in `wubble-engine/src/view.rs`; shell `TextInput` selections through Slint. (3) Reading back (a service that replaces the text) pastes through CEF's frame `paste` after it writes the pasteboard. (4) Register `NSApp.servicesProvider` only if wubble offers its own service ("Open URL in wubble"), with `NSServices` in `wubble-bundle`'s Info.plist. (5) Look Up: `showDefinitionForAttributedString:atPoint:` on the view at the selection's rect, from a "Look Up" row in the page context menu (`crates/wubble/src/menu.rs` rows, macOS only). Compile-check only.

## Second start: many URLs, local files, the working directory and the activation token (`instance-handoff`)

Key: `instance-handoff` · engine patch: no · state: not written.

Chrome opens every URL or file on its command line, resolves relative paths against the caller's working directory, and the running instance's window comes forward, even on Wayland. wubble's CLI takes one optional `page` (`crates/wubble/src/cli.rs`). `instance::Message` carries `Open(String)` or `Focus` (`crates/wubble/src/instance.rs`), the desktop entry's `%U` can pass several URLs, a relative `wubble page.html` is never turned into a `file://` URL, and `host.rs`:887 calls `focus_window()`, which Wayland compositors refuse without a fresh activation token. To build: (1) cli.rs: `page: Vec<String>`. Each argument that names an existing path (relative to the cwd, or absolute) becomes a `file://` URL (`url::Url::from_file_path`), and anything else goes through the omnibox rule as today. Put that in a pure `wubble_core` fn with tests. (2) A wire format v2 in `instance.rs`: `open <url>` lines repeated, then `token <xdg-activation token or DESKTOP_STARTUP_ID>`, then `end`, under `MAX_MESSAGE`. `parse_message` stays strict, an old single line is still accepted, and tests cover both. (3) The primary opens the first URL as today (a Little window) and the rest as tabs in it, or as new tabs in the last focused main window if that is the policy, matching Chrome's "new tab in the last window". (4) Activation: read `XDG_ACTIVATION_TOKEN`/`DESKTOP_STARTUP_ID` in the second start. On Wayland the worker (`wl/wayland.rs`, on the windows' connection) binds `xdg_activation_v1` and calls `activate(token, surface)`. On X11 send `_NET_ACTIVE_WINDOW` with the startup id's timestamp. On macOS and Windows call `NSApp activate` / `AllowSetForegroundWindow` from the second process.

## Command-line switches Chrome users expect (`chrome-switches`)

Key: `chrome-switches` · engine patch: no · state: not written.

Chrome users script the browser with `--new-window`, `--user-data-dir`, `--app=URL`, `--kiosk`, `--start-fullscreen`, `--start-maximized`, `--window-size=W,H`, `--window-position=X,Y`, `--proxy-server`, `--proxy-pac-url`, `--no-proxy-server`, `--proxy-bypass-list`, `--disable-gpu`, `--disable-extensions`, `--lang`, `--force-device-scale-factor`, `--remote-debugging-port` and `--enable-features`/`--disable-features`. wubble's clap `Cli` (`crates/wubble/src/cli.rs`) accepts only its own flags and rejects the rest. To build: (1) clap args with Chrome's names. `--user-data-dir` is an alias of `--profile`. `--new-window` forces a new main window, also through the instance socket (extend `instance::Message` with a NewWindow line). `--app=URL` opens a Little window (`WindowKind::Little`). `--kiosk`/`--start-fullscreen` start fullscreen with no sidebar. `--start-maximized`, `--window-size` and `--window-position` override `persist`'s saved geometry for the first window (`main.rs`:2140 `factory.open(..., geometry)`). (2) The Chromium pass-throughs (proxy, disable-gpu, lang, scale factor, feature lists) go into `EngineConfig`. A typed `Switches` struct is added in `wubble-engine/src/app.rs` `cef_config` after `CHROMIUM_SWITCHES`. User `enable-features`/`disable-features` are merged into `PageFeatures::switches`' single pair, never given twice (the comment at app.rs:512). `--disable-extensions` empties `config.extensions`. (3) `--remote-debugging-port` maps onto the existing debugging-port setting for this run only, so the MCP refusal rule (decisions.md "Debugging port and agents") still applies. Parse and mapping unit tests sit beside cli.rs's existing ones. `--help` lists them.

## Linux system packages: .deb, .rpm and an AUR PKGBUILD with the setuid sandbox (`linux-system-packages`)

Key: `linux-system-packages` · engine patch: no · state: not written.

Chrome ships .deb and .rpm. They install to /opt with `chrome-sandbox` setuid root, so the sandbox works on Ubuntu 23.10+ where `apparmor_restrict_unprivileged_userns` blocks user namespaces. wubble ships only a tarball through `install.sh` (no sudo), and TODO.md M7 lists "Ubuntu's user-namespace limit vs the no-sudo sandbox" (the warning is `linux_sandbox_warning` in `wubble-engine/src/app.rs`). To build: `scripts/release/package-linux-system.sh`, which takes the bundle `package-linux.sh` makes (`dist/wubble-<V>-linux-x86_64.tar.xz`) and produces (1) a .deb (with `dpkg-deb`, a `DEBIAN/control` with the CEF runtime's library dependencies, which `dpkg-shlibdeps` can compute) and (2) an .rpm (a `.spec` in `scripts/release/linux/`, `rpmbuild -bb`). Both install `/opt/wubble/`, `/usr/bin/wubble` as a link, the desktop entry and the hicolor icons, `chrome-sandbox` as root:root 4755 (postinst/%post), and an AppArmor profile `/etc/apparmor.d/wubble` allowing `userns` (Chrome's own) loaded in postinst when AppArmor is present. (3) `scripts/release/linux/PKGBUILD` for the AUR, from the same tarball and sha256. A system-package install has no `release.json` in the managed layout, so `updater/install.rs` `classify` reports `InstallKind::Elsewhere` and Settings shows updates as managed elsewhere. Check that the wording fits a package manager. Add a section to docs/release.md, and run shellcheck by hand.

To build: `scripts/release/macos/wubble.rb`, a cask that downloads `wubble-<V>-macos-<arch>.dmg` from the GitHub release with `sha256` per arch (`on_arm`/`on_intel`), `app "wubble.app"`, `auto_updates true` (wubble updates itself, so brew must not fight it), and a `zap` stanza for `~/Library/Application Support/wubble`, the caches and the preferences plist for `dev.wubble.browser`.
